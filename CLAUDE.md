## Риск-скоринг

### Единая модель — применяется ко ВСЕМ клиентам включая ПУВА/VASP

Источник: PDF «Риск-скоринг-модель для участников рынка виртуальных активов» + Приказ ГСФР 61/п (см. `docs/regulation/order-61p.md` — действующая редакция с учётом приказа № 26/п от 04.03.2026).

**Формула:** R = 0.25A + 0.25B + 0.25C + 0.25D  
Где каждый блок — среднее своих подкритериев (каждый 0–25 или 0–30/35 баллов):
- A = (A1+A2+A3+A4) / 4  — Профиль участника
- B = (B1+B2+B3+B4) / 4  — Активы и операции
- C = (C1+C2+C3+C4+C5) / 5  — Транзакционный риск
- D = (D1+D2+D3+D4) / 4  — Комплаенс и контроль

**Зоны:** 0–25 Низкий (GREEN), 26–50 Средний (YELLOW), 51–75 Высокий (ORANGE), 76–100 Критический (RED)

**Override-триггеры** (автоматически поднимают до CRITICAL):
- B2.5 Несоответствие SoF профилю
- B3.4 Прямая связь ≤1 hop с миксером
- B4.5 High-risk DEX pools (санкции/darknet)
- C4.5 Прямая связь с санкционным адресом ≤1 hop
- C5.4 High-risk пулы (fraud/darknet/ransomware)
- D1.5 Намеренный обход KYC/AML
- D2.4 Полное отсутствие учёта клиентских средств
- D3.5 Отказ от сотрудничества с регулятором
- A2.5 Отозванная лицензия
- A4.5 Связь с криминалом (ML/TF расследования)

**Подкритерии (варианты ответов с баллами):**

Блок A (0–100):
- A1 Юрисдикция: 0 (FATF member) / 0–15 (базовое рег.) / 20 (офшор) / 25 (FATF grey/black)
- A2 Лицензия: 0 (полная VASP) / 8–12 (MSB reg) / 15 (временная) / 25 (нет) / 25+override (отозвана)
- A3 UBO: 0 (полная идентификация) / 10 (частичная) / 15–20 (номиналы) / 25 (неизвестен) / +10 (PEP)
- A4 Репутация: 0 (позитивная) / 5–8 (нейтральная) / 15 (негативные упоминания) / 20–25 (нарушения) / 25+override (криминал)

Блок B (0–100):
- B1 Тип активов: 0–5 (BTC/ETH) / 5–8 (стейблкоины) / 10–15 (альткоины) / 25–30 (privacy coins) / 25–30 (неизвестные токены)
- B2 SoF/SoW: 0 (полная документация) / 8–12 (частичная) / 20 (self-declaration) / 30–35 (отказ) / 35+override (несоответствие профилю)
- B3 Миксеры: 0 (нет) / 10–15 (единичное >2 hops) / 30–35 (регулярное) / 35+override (≤1 hop)
- B4 DEX: 0 (только CEX) / 5 (регулируемые DEX с KYC) / 10–12 (популярные DEX) / 18–20 (обход CEX→DEX) / 20+override (high-risk pools)

Блок C (0–100):
- C1 Объёмы: 0–3 (соответствие профилю) / 8–12 (превышение 2–5x) / 15–20 (>5x) / 18–20 (smurfing)
- C2 Частота: 0–2 (<10/мес) / 5 (10–100/мес) / 10–12 (100–1000/мес) / 15–18 (>1000, batching) / +5 (thin hours)
- C3 География: 0–3 (одна низкорисковая) / 5–8 (несколько регулируемых) / 15–18 (офшоры) / 22–25 (FATF grey/black) / +5 (частая смена)
- C4 Контрагенты: 0–2 (верифицированные CEX) / 8–10 (частично) / 15–18 (>70% unhosted) / 18–20 (2–3 hops от санкций) / 20+override (≤1 hop)
- C5 Пулы: 0 (не использует) / 3–5 (легитимные) / 10–12 (unaudited) / 15+override (high-risk fraud/darknet)

Блок D (0–100):
- D1 AML/KYC: 0–2 (полная программа) / 8–12 (базовые процедуры) / 18–22 (частичное KYC) / 25–30 (нет политик) / 30+override (обход)
- D2 Учёт средств: 0 (полная сегрегация) / 10–15 (частичная) / 20–25 (нет раздельного учёта) / 25+override (нет учёта вообще)
- D3 Отчётность: 0–2 (проактивная) / 5–8 (регулярная) / 15–18 (нерегулярная) / 22–25 (отсутствует) / 25+override (отказ от сотрудничества)
- D4 Реакция на запросы: 0–2 (<24 часа) / 5–8 (1–3 дня) / 12–15 (>5 дней) / 18–20 (игнорирование)

**Текущее состояние реализации:**

- Фронт (`RiskScoring.tsx`): чекбоксы high/low — **нужно переписать под 4-блочную форму**

## Бизнес-контекст

Система — платформа для оператора виртуальных активов (ПУВА/VASP) в Кыргызстане. Регулятор — ГСФР. Полный перечень применимых НПА — в разделе «Регуляторные источники».

### Этап развития

Продукт находится в процессе расширения от инструмента комплаенс-офицера до полнофункциональной платформы ПУВА с тремя контурами:

- **Клиентский портал** — самостоятельный KYC (ФЛ/ЮЛ/нерезидент), загрузка документов, подача и трекинг заявок на операции, RFI.
- **Бэк-офис операционистов** — приём и исполнение заявок, фиксация курсов/контрагентов/кошельков, ведение реестра операций по форме ГСФР.
- **Комплаенс** — текущий функционал (KYC-проверка, скрининг, риски) + сквозная видимость операций, KYT-флаги, формирование сообщений в ФР.

### Целевые SKU

Архитектура должна допускать раздельную продажу:

- **Compliance Suite** — текущий функционал + БВ + STR + регуляторная база.
- **VASP Operations** — клиентский портал + бэк-офис + реестр операций.
- **Full VASP Platform** — полная сборка.

### Типы клиентов системы

- **Физические лица** — стандартная анкета по Положению о CDD (постановление КМ КР от 14.11.2025 № 739).
- **Юридические лица** — анкета + БВ-структура.
- **VASP / ПУВА (как контрагенты)** — 4-блочный скоринг + EDD.

## Безопасность работы Claude Code

Проект работает с данными клиентов финансовой организации под надзором ГСФР. Любая утечка или порча данных = регуляторный инцидент.

### Жёсткие запреты (никогда без явной просьбы пользователя)

- Подключение к любой БД кроме локальной `compliance_db` на `localhost:5433`. Никаких прод-хостов, staging, реплик.
- `git commit`, `git push`, `git push --force`, `git reset --hard`, переключение веток.
- `rm -rf`, `DROP TABLE`, `DROP DATABASE`, `TRUNCATE`, `alembic downgrade`.
- Чтение, вывод в чат или редактирование `.env`, `.env.*`, любых файлов с секретами.
- Установка зависимостей с непроверенных источников. Только `pip install` из `requirements.txt` и `npm install` из `package.json`.
- Любые сетевые запросы к внешним API из кода без явного обсуждения.

### Требуют подтверждения перед выполнением

- `alembic upgrade head` и любые миграции — сначала показать diff сгенерированной миграции.
- Удаление или переименование существующих файлов.
- Массовые правки (>5 файлов за один шаг).
- Изменения в `backend/app/routers/sanctions.py` и `sanctions_loader.py` — санкционный модуль критичен, ломать нельзя.

### Соглашения по миграциям (Phase 1 — manual, Phase 2 — Alembic)

**Phase 1 (текущая):** Alembic ещё не настроен (Q-meta-D). Миграции пишутся вручную как:

- SQL файлы в корне (исторический паттерн): `migrate_risk_level.sql`, `migrate_risklevel_normalize_case.sql`. Будут перенесены при настройке Alembic — Q-meta-E.
- Python-скрипты в модулях: `app/audit/migrate_legacy.py`, `app/rbac/migrate_user_roles.py` — CLI-утилиты с `--dry-run` / `--commit` / `--force`.

Каждая миграция — атомарная, одна логическая единица. Перед apply — показать SQL/код и дождаться подтверждения.

**Phase 2 (запланировано):** настройка Alembic + retroactive baseline. После этого правило: только `alembic revision --autogenerate -m "..."`, manual migrations — исключение. В сообщении — префикс этапа: `"phase-2: add ubo tables"`.
