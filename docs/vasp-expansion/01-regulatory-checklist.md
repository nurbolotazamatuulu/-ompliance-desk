## Условные обозначения

- **Статус:** `ЕСТЬ` — реализовано полностью; `ЧАСТИЧНО` — реализована часть; `НЕТ` — не реализовано
- **Регуляторный риск** (для пробелов): 🔴 высокий — норма прямого действия, нарушение = санкции ГСФР; 🟡 средний — норма требует процедуры, можно частично заменить ручной работой; 🟢 низкий — формальное требование, легко закрывается
- **Целевой модуль:** `KYC` / `Sanctions` / `Risk` / `Transactions` / `FIU-Reporting` / `Freezing` / `RFI` / `ClientPortal` / `BackOffice` / `Audit` / `Infra` / `HRC` (high-risk countries) / `RemoteID` (дистанционная идентификация)

### III.1.ter Compliance при делегировании функций третьим лицам

> **Регуляторный фон.** В НПА КР делегирование покрыто частично:
> - **ЗВА ст. 27 п. 4** (прямая норма): «Для расширения спектра предоставляемых услуг поставщики услуг виртуальных активов могут привлекать **только других поставщиков услуг виртуальных активов** в качестве агентов». То есть в качестве **агента** ОВА может привлекать только лицензированный VASP в КР.
> - **ПОВА п. 7.1** (обязательное делегирование): использование внешнего AML/KYT-провайдера, определённого уполномоченным органом, является обязательным.
> - **Не покрыто прямо:** использование внешних SaaS-инструментов для custody (Fireblocks, BitGo, Copper), для дистанционной идентификации (Sumsub, Onfido), для блокчейн-аналитики (Chainalysis, TRM Labs). Юридически они не являются «агентами» — это инструменты, ответственность за compliance остаётся целиком на ОВА. Этот пробел закрывается продуктовой логикой и внутренней политикой ОВА, а не регулятором.
> - **Q15 (новый, см. раздел VII):** официальная позиция ГСФР по разграничению «агент» vs «внешний инструмент SaaS» для custody/RemoteID/блокчейн-аналитики.

## Раздел VII — Открытые вопросы

Эти вопросы требуют решения **до** перехода к шагу 2 (доменная модель).

### Q1. Пороги дроппер-детектора (Приказ 26/п § 3 п. 15)

В НПА сформулировано «большое количество операций / физических лиц», «короткий промежуток (≤1 минуты)», «ночное время» — без конкретных значений.

**Требуется решение:** числовые пороги по умолчанию (например, >50 операций/день, >20 уникальных лиц/день, ночное время = 22:00-06:00 по часовому поясу клиента или по UTC+6) либо настраиваемые в `Settings` для каждой компании.

### Q2. Полный справочник кодов 40001-40088 и 10000-38099

В коде (`transactions.py`) есть основа, но не уверен, что покрыты все коды и их описания соответствуют последним методическим указаниям ФР.

**Требуется решение:** где взять авторитетный справочник (запрос в ГСФР? публикация на сайте ФР? внутренний документ?). Без него невозможно гарантировать корректную автогенерацию СТР.

### Q3. Веса критериев в риск-модели 61/п

НПА перечисляет критерии без баллов. Сейчас веса заданы в коде эмпирически.

**Требуется решение:** кто формально утверждает веса — ФР (если есть утверждённая методика, нужно её прислать) или сам ОВА в правилах внутреннего контроля (тогда нужен документ внутреннего контроля).

### Q4. Override-триггеры — явный список «hard-stop без апелляции»

В коде есть 8 триггеров (миксер ≤1 hop, отозванная лицензия и т.д.). НПА не определяет жёсткий список.

**Требуется решение:** утвердить ли текущий список как часть правил внутреннего контроля или согласовывать с ГСФР.

### Q5. АРМ для отправки СТР

Как именно отправляются СТР сейчас (ручная загрузка через web-кабинет ФР? АРМ-приложение от ГСФР?).

**Требуется решение:** какой целевой канал (АРМ-API, REST-эндпоинт ФР, защищённая email-схема), какой формат (XML-схема, JSON), какая ЭЦП (ГОСТ-2012, eToken, программная подпись?).

### Q6. Дистанционная видеоверификация — интеграция с госсервисами КР

ПCDD прил. 5 требует сверки с государственными электронными сервисами, но не называет конкретные.

**Требуется решение:** Тундук? Электронный паспорт? ГРС? Какие API доступны и что нужно для подключения (договор с уполномоченным органом).

### Q7. Согласование информационных систем для верификации иностранцев

ПCDD прил. 5 п. 26: «согласование с органом финансовой разведки и соответствующим проверяющим органом».

**Требуется решение:** есть ли утверждённая процедура согласования? Можно ли использовать Sumsub / Onfido / другие? Какие требования к согласованной системе.

### Q8. Анкета 606 → 739: дельта полей

Постановление 606 утратило силу. Текущая модель `IndividualClient` / `LegalEntityClient` сделана по 606. Нужна миграция.

**Требуется решение:** план миграции (конкретные новые поля, удаление неактуальных, переименование). Подготовить как часть шага 2.

### Q9. Перечень низкорисковых разовых операций

Положение о CDD упоминает «перечень определяется ФР», но сам перечень не приложен.

**Требуется решение:** запросить документ или согласиться использовать критерии низких рисков из 61/п (гл. 2) как proxy.

### Q10. «Процентный скоринг» (ПОВА п. 7.1, 24)

ПОВА говорит «использование AML/KYT-инструментов поставщика, определённого уполномоченным органом». Уполномоченный орган не назвал конкретного провайдера.

**Требуется решение:** какой провайдер AML/KYT для блокчейна (Chainalysis / TRM Labs / Range / Elliptic / CipherTrace) — это влияет на модели данных (поля для wallet-tags, hop-distance, risk score blockchain) и стоимость.

### Q11 (бонус). Что считать «операцией с виртуальными активами» для применения порога 1М сомов

ПФР прил. 1 п. 7 указывает порог 1М сомов для «купля-продажа/обмен/перевод» виртуальных активов. Не уточняется, агрегируется ли это по периоду (день/неделя/единичный) или применяется к каждой операции отдельно.

**Требуется решение:** интерпретация — единичная или агрегат за период.

### Q12 (бонус). Применимость хранения 7 лет к ОВА

ПФР § 44 говорит о 7-летнем хранении сообщений в ФР, но в основном для финансовых учреждений в узком смысле. Применимо ли к ОВА (нефинансовая категория)?

**Требуется решение:** уточнить срок хранения СТР и квитанций для ОВА (5 или 7 лет).

### Q15 (критично). Разграничение «агент» vs «внешний инструмент SaaS» в контексте custody/RemoteID/блокчейн-аналитики

ЗВА ст. 27 п. 4 разрешает привлекать в качестве **агентов** только лицензированных VASP в КР. Но норма не разъясняет, считается ли использование внешнего SaaS-инструмента (Fireblocks для custody, Sumsub для дистанционной идентификации, Chainalysis для блокчейн-аналитики) «привлечением агента» или это просто использование инструмента (как любая другая технология).

**Различие принципиально:**
- Если **агент** — нельзя использовать non-VASP, что отрезает почти все доступные на рынке custody/RemoteID-провайдеры (они не имеют лицензии VASP в КР)
- Если **инструмент** — можно использовать, но ответственность за compliance и сохранность данных остаётся на ОВА

**Требуется решение:** официальная позиция ГСФР (письменное разъяснение или прецедент). До получения позиции — консервативная интерпретация: SaaS-инструмент допустим только для custody/RemoteID/AML-KYT (не как агент), при выполнении трёх условий: (1) договор с провайдером оформлен; (2) данные дублируются локально (см. строки 114g3-g6); (3) провайдер не действует от имени ОВА перед клиентом.

### Q14 (критично). Что считать «письменным поручением» владельца на перемещение ВА

ЗВА ст. 26 п. 5: «перемещение виртуальных активов осуществляется только по письменному поручению владельца». Норма не специфицирует форму поручения — это толкование на стороне правоприменителя.

**Требуется решение:** какие из форм юридически достаточны (выбрать одну или несколько)?
- (а) Бумажное поручение с собственноручной подписью клиента в офисе ОВА — самое консервативное толкование, ограничивает онлайн-сценарии
- (б) Электронный документ с квалифицированной электронной подписью (ЭЦП) клиента — требует интеграции с УЦ КР
- (в) Действие в личном кабинете с MFA-подтверждением (TOTP / SMS / push) — практическая норма большинства международных VASP, юридически закреплена в КР через Закон об ЭЦП и Закон о ЭКР как «электронное волеизъявление»
- (г) Комбинированный режим: для сумм до X — (в); для сумм выше X — (б) или (а)

Это блокирующее решение для строки 114f и для архитектуры клиентского портала. Без ответа невозможно проектировать UX вывода.

### Q13 (критично). Custody-модель: hot/cold/MPC/non-custodial

ЗВА ст. 26 п. 5 требует одновременно: (а) сохранность ВА и приватных ключей; (б) возможность самостоятельного перемещения клиентом; (в) перемещение только по поручению владельца. Это влияет на архитектуру кардинально.

**Требуется решение:** какую custody-модель строим?
- Полностью custodial (мы держим ключи, клиент даёт поручения через UI) — стандартный VASP-подход
- Non-custodial (клиент держит свои ключи, мы только сводим контрагентов) — DEX-подход
- Гибрид (hot wallet для ликвидности + cold storage + MPC для подписей)
- Интеграция с готовым кастоди-провайдером (Fireblocks, BitGo, Copper) — ускорение времени до выпуска
Это блокирующее решение для шага 3 (архитектура) — без него нельзя проектировать ни ClientPortal, ни BackOffice.
